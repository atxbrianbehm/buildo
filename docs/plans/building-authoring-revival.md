## Product outcome

Buildo should let an artist create a convincing building, keep it visible while editing, change a particular architectural part or surface, and save a project they can reopen and continue. A prompt proposes a starting composition; precise controls and authored choices retain authority afterward.

The first usable release stays with the existing rectangular late-19th-century commercial/apartment family. Its data remains labelled demo. It must support an ordinary three-quarter view, competent side/rear elevations, believable openings and trim, correctly scaled materials, exact floor/bay edits, selected-component edits, semantic surface composition, undo, and save/reopen.

The broader idea is still **geometry operations producing meaningful architectural scopes, with material composition bound to those scopes**. For example: split a front facade into floors and bays, place openings, then assign masonry to walls, painted material to frames, and weathering to selected trim. Geometry and surface appearance are sibling outputs; pixels never determine structure.

A full Geometry Nodes clone is unnecessary. A small, genuinely executable building graph is useful. Its visual editor follows working operators and semantic editing, rather than preceding them.

## Dynamic generation and UTDG remain product requirements

**Direction reaffirmed by the user 2026-10-17.** The reviewed C4 building is a quality baseline and one starting recipe. Buildo must continue toward dynamically generated, editable buildings informed by UTDG. The product must not depend on this one building's dimensions, palette or fixed node arrangement as its only generative result.

The broader [UTDG responsibility map](https://app.notion.com/p/3a7b77d6cd4f81868a4fddfafe285aa6) assigns UTDG source-backed priors, compatibility, confidence, provenance and intentional exceptions. Its [current project page](https://app.notion.com/p/3fab77d6cd4f8134b956ff3b65e50a74) describes a historical reference graph, starting with clothing. Building-domain coverage and a usable architecture query contract are not established by that description.

Buildo's older `utdg/textureDescriptionContracts.ts` and `docs/research/utdg-late19c-v0.1.json` are a narrow, schema-validated material research brief. They are useful starting inputs, not evidence that the current UTDG service is integrated or that architectural claims are sourced. Keep the existing material-lane boundary while preparing an adapter to the broader reference system; do not silently equate these two contracts.

The bounded dynamic-generation / UTDG packet uses these acceptance criteria:

1. Start from the existing validated brief and a versioned, pinned reference snapshot or explicit demo fixture. Preserve source IDs, evidence locators, confidence, review status and observed/inferred/generated distinctions. Do not assume a public endpoint or claim architectural coverage before checking the actual data.
2. Resolve supported recipe/style/material choices into the same editable construction graph. A second supported input must produce a meaningful architectural or material difference through executed operators, without adding preassembled meshes or special-casing the reviewed screenshot.
3. Reproduce the same resolved source for identical snapshot, recipe version, semantic seeds and locks. Reroll only declared unlocked choices; compatible regeneration retains accepted edits and surviving semantic identities. Diagnose conflicts rather than silently dropping locks.
4. Bind UTDG material roles and physical scale to the existing atlas/trim-sheet planner and semantic compositor. Appearance-only changes preserve structural positions, topology and transforms; structure-only changes reuse unchanged material artifacts. Treat proposed `TrimSheetPlan` consumption as unimplemented until proved.
5. Version and runtime-validate the saved reference bindings, recipe/resolution identity and explicit overrides. Save/Open and cold recovery retain resolved source and pinned dependencies even when UTDG is unavailable; reconnecting or refreshing reference data cannot silently rewrite an accepted project. Unknown coverage remains visible, and intentional historical exceptions remain authored choices.
6. Verify parameter causality, bounded seeded variation, lock preservation, material/geometry independence, failed/stale-resolution retention and portable recovery in the actual workbench. Render and review the supported results on both backends before claiming a UTDG-driven workflow.

## Keep these architectural boundaries

- Keep React, Three.js, Zustand, Zod, the compiler worker and the existing feature boundaries. Core/contracts/compiler remain renderer- and browser-independent.
- Extend [FacadeSplitPlan](../../src/features/building-family/compiler/facadeSplitPlan.ts) as the single wall/opening authority. Do not add a parallel placement system.
- Keep deterministic semantic seeds, shared family resources and geometry/material invalidation. Floor/bay/component edits must preserve unaffected material content hashes.
- Keep the artifact registry, IndexedDB and completed-family export foundations. Do not store Three.js objects or large buffers in the authored state.
- Continue primitive/profile/recipe construction. Do not introduce preassembled facade or component meshes.
- Preserve PSG v2 compatibility. Intent generation proposes values; an explicit authored edit wins unless a documented constraint rejects it with a visible diagnostic.
- Keep remote generation optional and server-only. A usable procedural/local-material workflow must not require provider credentials.

BuildingDocument is the writable source. BuildingFamilySpec, facade/split plans and runtime artifacts are derived. During the initial parameter workflow the document owns explicit values and scope overrides. As supported graph operators arrive, their parameters become the source for the corresponding fields; inspector commands edit those same parameters. Never keep independently writable graph width, global width and spec width. Version the transition and keep unsupported legacy graph data descriptive until migrated.

Separate document/revision identity, structural identity and surface identity. A material edit can change document and surface hashes while preserving structural positions, topology and transforms. Family-wide material sources/atlas defaults are distinct from per-scope surface bindings: the existing renderer assigns a material at batch level, so changing a shared trim slot cannot selectively weather one trim piece. Add a derived binding/override artifact, applied with compatible batching or per-instance data, while reusing unchanged shared source artifacts.
