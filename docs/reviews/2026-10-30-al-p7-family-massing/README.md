# AL.P7.0: Family massing variation

An opt-in, seeded demo policy chooses two, three or four storeys and three, four or five bays for each member. The existing generation resolver receives those counts, records them in that member's generation source and produces the executed graph; the composition plan refuses to apply a massing choice to a graph generated with different counts. Family source 0.7 preserves the plan. Selected-member details report actual counts. The policy rejects footprint/storey locks, pinned counts or authored count changes that would be overwritten, and existing retained local targets must still fit the generated member.

Focused tests cover deterministic plan replay and tampering, executed graph and lineage agreement, locks, imported pins and grouped targets that would disappear. Both [WebGPU](webgpu-01/receipt.json) and [WebGL](webgl-01/receipt.json) generated the same six massing and storefront combinations, edited one member, retained siblings and source, and saved/reopened the family without new material-provider calls. The [family](webgpu-01/family.png) and [edited member](webgpu-01/member.png) are actual textured captures. The silhouettes and bay counts are visibly different, but the shared brick material and repeated facade details remain far narrower than the supplied street references. This is not parcel or street placement, historical evidence, or visual acceptance; the previously noted sill line still needs closer review.

Full repository validation is pending. The capture script generates its own starting construction through the editor.
